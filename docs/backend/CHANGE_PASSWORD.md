# CRA-33 회원 비밀번호 변경

일반 회원이 기존 비밀번호를 확인한 뒤 새 비밀번호로 바꾸는 FastAPI API입니다.
성공하면 현재 기기를 포함한 모든 로그인 계열을 폐기합니다. 관리자 비밀번호 변경,
비밀번호 찾기·재설정, BFF와 화면 구현은 포함하지 않습니다.

## 요청과 응답

`POST /api/v1/auth/change-password`

검증된 회원의 `Authorization: Bearer <Access JWT>`가 필요합니다. 변경 요청에는 기존
CSRF 정책에 맞는 Origin 또는 신뢰된 BFF 공유키가 필요합니다. 사용자 ID를 받지 않고
JWT의 `sub`를 사용합니다. 관리자 principal 또는 admin permission이 있으면 거절합니다.

```json
{
  "currentPassword": "현재 비밀번호",
  "newPassword": "새 비밀번호 8~256자"
}
```

| 결과                                                  | 상태 | 처리                                  |
| ----------------------------------------------------- | ---- | ------------------------------------- |
| 성공                                                  | 204  | 본문·새 토큰·Set-Cookie 없음          |
| 현재 비밀번호 불일치 또는 동시 변경으로 해시가 달라짐 | 400  | `CURRENT_PASSWORD_INVALID`            |
| 미인증·무효/폐기 JWT·관리자·비활성/삭제 회원          | 401  | 기존 일반 오류와 Bearer 인증 헤더     |
| CSRF 차단                                             | 403  | 기존 공통 오류                        |
| 누락·null·추가 필드·잘못된 타입/길이/문자 인코딩      | 422  | 입력값을 포함하지 않는 일반 검증 오류 |
| 저장소 실패                                           | 503  | 비밀번호 변경 성공으로 처리하지 않음  |

400 오류의 JSON은 다음과 같습니다. 현재 비밀번호 오류를 401로 처리하지 않아
브라우저의 인증 갱신 로직이 비밀번호 변경을 재시도하는 일을 피합니다.

```json
{ "error": { "code": "CURRENT_PASSWORD_INVALID", "message": "현재 비밀번호를 확인해 주세요." } }
```

## 파일별 역할과 보안

- `apps/api/aura_api/api/auth.py`: SecretStr 입력 검증, 기존 회원 principal 검사, HTTP 응답.
- `apps/api/aura_api/identity/service.py`: 기존 Argon2id 검증·해시 함수 재사용. 직접 호출에도
  길이·UTF-8 인코딩을 검사합니다. 원문 공백·한국어·이모지를 보존합니다.
- `apps/api/aura_api/identity/repository.py`: 회원 ID 조회, 원자적 비밀번호 변경 인터페이스.
- `apps/api/aura_api/identity/postgres.py`: 비밀번호 저장과 모든 계열 폐기를 한 트랜잭션으로
  처리합니다. 기존 users/password_hash, auth_token_families, refresh_tokens, revoked_tokens만
  사용하므로 새 스키마·ORM·마이그레이션은 필요하지 않습니다.
- `apps/api/tests/test_change_password.py`: 기존 lifecycle fixture를 재사용해 API·동시성·DB 롤백 검증.
- `apps/api/tests/test_principal_boundaries.py`: 회원과 관리자 UUID가 같아도 관리자 차단 검증.

비밀번호는 8~256자 외에 새로운 복잡도 규칙을 추가하지 않습니다. 현재 비밀번호는 기존
로그인과 같이 1~256자 입력을 허용합니다. strip이나 Unicode 정규화를 하지 않습니다.
기존과 같은 새 비밀번호도 허용하되 해시를 새로 만들고 모든 계열을 폐기합니다.
비밀번호·해시·토큰을 출력하는 로깅을 추가하지 않았습니다. 입력·저장소 예외의 원문은
공개 응답에 넣지 않으며 민감정보 응답·로그 비노출 테스트를 둡니다.

## 트랜잭션과 동시 요청

트랜잭션(여러 DB 변경을 모두 성공시키거나 모두 취소하는 단위)은 다음 순서입니다.

1. 서비스에서 현재 Argon2id 비밀번호 확인과 새 해시 계산을 수행합니다.
2. 저장소가 회원 행을 `FOR UPDATE`로 잠급니다. 회원이 활성 상태인지, 검증 당시 해시가
   지금도 같은지 재확인합니다. 다른 요청이 먼저 변경했다면 변경하지 않습니다.
3. 비밀번호 해시를 저장합니다.
4. 같은 회원의 모든 계열을 ID 순서로 잠그고 기존 `_revoke_family()`를 호출합니다.
5. 계열과 Refresh를 폐기하고 모든 미만료 Access jti를 기존 revoked_tokens에 기록합니다.
6. 커밋이 끝나야 성공합니다. 중간 실패는 해시·계열·Refresh·폐기 기록을 모두 롤백합니다.

잠금 순서는 회원 → 계열 → 토큰입니다. 로그인과 Refresh는 회원을 `FOR SHARE`로 잠그므로
비밀번호 변경과 서로 기다립니다. 로그인은 비밀번호를 검증한 해시를 저장 단계에 전달하고
회원 잠금 아래 현재 해시와 다시 비교합니다. 따라서 이전 비밀번호로 검증만 마친 로그인은
변경 후 새 계열을 만들 수 없습니다. 로그인이 먼저 커밋했다면 비밀번호 변경이 그 계열도
폐기합니다. Refresh가 먼저 회전했으면 새 토큰까지 폐기하고, 변경이 먼저면 회전을 거절합니다.

다른 회원 계열과 `admin_sessions`는 변경하지 않습니다. 커밋 이후 새로 검증하는 기존 토큰은
거절되지만 이미 인증을 완료해 실행 중인 다른 업무 요청을 강제로 취소하는 기능은 아닙니다.
폐기 기록의 정리는 기존 보존 정책을 따라야 하며 살아 있는 Access 발급 기록을 조기 삭제하면
안 됩니다. 비밀번호 변경 후 새 비밀번호로 로그인하면 새 계열을 생성할 수 있습니다.

## 검증과 연계

DB 없는 전체 검사는 `npm run check:api`로 수행합니다. PostgreSQL 검사는 실행 중인
`aura-jwt-test-db`가 `127.0.0.1:5434`로만 연결되는지 확인하고, 전용 접속 정보와
`AURA_ALLOW_DATABASE_TESTS=1`을 설정한 경우에만 `tests/test_change_password.py`를 실행합니다.
기존 lifecycle fixture가 매 테스트마다 임의 이름의 스키마를 만들고 그 스키마만 정리합니다.
운영·공유 DB에 연결하거나 마이그레이션 롤백을 실행하지 않습니다.

정민님 연계: BFF 경로와 화면에서 기존 인증 Web Lock을 재사용하고, 204 확인 후 쿠키 삭제와
사용자 상태 초기화·재로그인 안내를 구현해야 합니다. 400은 Refresh 재시도 대상이 아닙니다.
다라님 연계: 배포 DB의 기존 인증 테이블 적용과 환경 설정 확인이 필요합니다.
우섭님 연계: 기존 스키마·ORM·관리자 구현은 수정하지 않습니다.

2026-10-27 검증 결과는 다음과 같습니다. 서로 다른 실행에 포함된 같은 테스트는 합산하지 않습니다.

| 실행                                                                         | 통과 | 실패 | 건너뜀 |
| ---------------------------------------------------------------------------- | ---: | ---: | -----: |
| `npm run check:api`의 전체 pytest, DB 실행 비활성화                          |  549 |    0 |    127 |
| 비밀번호 변경·기존 lifecycle·프로필 검사, 메모리와 격리 PostgreSQL 함께 실행 |  174 |    0 |     10 |
| `npm run check:web`의 웹 테스트                                              |  138 |    0 |      0 |
| `npm run test:e2e:jwt`                                                       |    6 |    0 |      0 |

Ruff 검사와 Python 109개 파일의 포맷 검사가 통과했습니다. 실제 PostgreSQL에서는 로그인·
회전·전체 폐기·같은 UUID의 관리자 세션 유지·부분 폐기 후 롤백을 검증했습니다. 비밀번호
변경이 회원 잠금을 가진 동안 이전 비밀번호 로그인과 Refresh를 기다리게 한 뒤, 변경 커밋
후 두 요청이 모두 거절되는 것도 검증했습니다. 메모리 테스트로 DB 잠금을 검증했다고
표시하지 않습니다. DB 전용 테스트를 메모리 매개변수로 실행한 경우 등은 건너뜁니다.

전체 API 검사는 DB 접속을 명시적으로 비활성화하므로 기존 DB 스키마·업무 API 테스트와
PostgreSQL 매개변수가 건너뜁니다. 기존 Windows asyncio 정책 폐기 예정 경고 2개가 있습니다.
JWT E2E는 실제 FastAPI 라우터·검증기와 Next.js BFF를 사용하지만 저장소는 테스트 대역입니다.
새 비밀번호 변경 BFF 경로와 화면은 없으므로 새 기능의 브라우저 E2E는 후속 작업입니다.

`npm run build`는 통과했습니다. 로컬 설치된 Next.js는 16.4.2이며 저장소 선언/잠금의
16.4.3과 달라, 잠금 파일과 동일한 깨끗한 환경의 빌드는 CI에서 추가 확인해야 합니다.
루트 `npm run check`는 기존 273개 파일의 Prettier 경고로 포맷 단계에서 중단됩니다.
이번 변경 문서는 별도로 포맷 검사하며 무관한 기존 파일은 일괄 수정하지 않습니다.
