# 결제 완료 주문 취소와 전액 환불 (마이그레이션 0009)

결제가 끝난(`paid`) 주문을 회원이 취소하면 토스페이먼츠에 전액 취소를 요청하고, **PG가 환불을 확인한 뒤에만**
주문을 `cancelled`로 바꾸며 재고·쿠폰을 되돌립니다. 미결제 주문 취소는 그대로입니다
([미결제 주문 취소](ORDER_CANCELLATION.md)).

## 범위와 정책 결정

| 항목           | 이번 구현                                                 | 팀 확정이 필요한 것                        |
| -------------- | --------------------------------------------------------- | ------------------------------------------ |
| 취소 가능 상태 | `paid`만. `preparing`·`shipped`·`delivered`는 409         | 상품 준비 중 취소를 허용할지, 위약 처리    |
| 환불 금액      | 결제 금액 전액(배송비 포함). 클라이언트 값은 받지 않음    | 부분 환불·배송비 정책                      |
| 쿠폰           | 미결제 취소와 같게 이 주문이 쓴 쿠폰만 `AVAILABLE`로 복구 | 환불 시 쿠폰 복구 여부(현재는 복구)        |
| 재고           | 주문 접수 때 차감한 만큼 복구(미결제 취소와 같은 규칙)    | 반품 상품의 재판매 가능 여부(배송 후 취소) |
| 취소·환불 주체 | 회원 본인만. 관리자 취소는 없음                           | 관리자 취소·CS 환불 절차                   |
| 결제수단       | 카드·계좌이체 등 환불 계좌가 필요 없는 수단               | 가상계좌 환불(`refundReceiveAccount`)      |

배송 이후 취소와 부분 환불은 정책이 정해지지 않아 **구현하지 않고 거절**합니다. 쿠폰 복구는 기존 미결제 취소
정책을 그대로 쓰되, 환불 시 복구가 맞는지는 별도 확정이 필요합니다.

## 흐름 (PG 호출 중 DB 트랜잭션 없음)

```
1. 확인 (짧은 트랜잭션)   주문·결제 잠금 → 소유자·상태 확인 → refunds 행(IN_PROGRESS, 금액=결제 금액) 기록
2. PG 취소 (트랜잭션 밖)  POST /v1/payments/{paymentKey}/cancel, Idempotency-Key = 환불 ID
3. 기록 (짧은 트랜잭션)   환불 완료 → refund DONE + 주문 cancelled + 이력 + 쿠폰·재고 복구 (한 번에)
```

| PG 결과                                      | 환불 행                       | 주문        | 응답                              |
| -------------------------------------------- | ----------------------------- | ----------- | --------------------------------- |
| 취소 완료(`CANCELED`, 취소 합계 = 결제 금액) | `DONE`                        | `cancelled` | 200                               |
| 확정 거절(`NOT_CANCELABLE_PAYMENT` 등)       | `FAILED`                      | `paid` 유지 | 409 `REFUND_FAILED` (재시도 가능) |
| 타임아웃·5xx·처리 중·응답 불명               | `IN_PROGRESS` 유지            | `paid` 유지 | 202 (같은 요청을 다시 보냄)       |
| 취소 금액이 전액과 다름·`PARTIAL_CANCELED`   | `IN_PROGRESS`+`review_reason` | `paid` 유지 | 202 (사람이 확인)                 |

결과를 알 수 없는 경우는 실패로 처리하지 않습니다. 같은 요청을 다시 보내거나 재확인 작업이 **같은 멱등키**로
다시 물어 PG가 첫 결과를 돌려주게 합니다.

## 중복 환불과 동시 요청 방어

- 주문 행 잠금으로 동시 요청이 직렬화됩니다. 결제당 `IN_PROGRESS`·`DONE` 환불은 1건만
  (`refunds_payment_active_key` 부분 유니크 인덱스).
- 진행 중인 환불이 있으면 새로 만들지 않고 **같은 환불 ID(멱등키)**로 PG에 다시 묻습니다. 동시에 들어온
  요청은 PG가 처리 중 오류를 돌려주면 202가 됩니다.
- 이미 환불·취소된 주문에 다시 요청하면 PG를 호출하지 않고 200(`cancelled`)입니다.
- `FAILED` 뒤의 재시도는 새 환불 행·새 멱등키입니다. 이전 요청이 실제로는 성공했더라도 토스가
  `ALREADY_CANCELED_PAYMENT`로 거절하고, 서버는 결제를 조회해 **취소 합계가 결제 금액과 같을 때만** 환불
  완료로 받아들입니다(두 번째 환불은 일어나지 않습니다).
- 환불 진행 중에는 그 주문의 상태를 다른 경로(관리자 등)로 바꿀 수 없습니다(409 `REFUND_IN_PROGRESS`).
- 환불 기록 중 DB 오류가 나면 전부 롤백되고 환불은 `IN_PROGRESS`로 남아 재요청·재확인 작업이 마무리합니다.

## API (계약 1.4.0)

`POST /api/v1/orders/{orderId}/cancel` (회원 JWT, CSRF) — 기존 경로를 확장했습니다.

| 상황                                | 응답                                                |
| ----------------------------------- | --------------------------------------------------- |
| 미결제 취소·환불 완료·이미 취소됨   | 200 `OrderOut` (`status: "cancelled"`)              |
| 환불 결과 확인 중                   | 202 `OrderOut` (`status: "paid"`), 같은 요청 재전송 |
| PG가 환불을 거절                    | 409 `REFUND_FAILED`                                 |
| 환불 확인 중 주문 상태 변경 시도    | 409 `REFUND_IN_PROGRESS` (관리자 상태 변경)         |
| 준비 중·배송 중·배송 완료·취소 불가 | 409 `ORDER_NOT_CANCELLABLE`                         |
| 결제 확인 중(미결제 주문)           | 409 `PAYMENT_IN_PROGRESS`                           |
| 다른 회원·없는 주문                 | 404 `ORDER_NOT_FOUND`                               |
| 결제 완료 주문인데 PG 설정이 없음   | 503 (환불됐다고 가정하지 않음)                      |
| 비로그인·관리자 토큰                | 401                                                 |

PG의 오류 코드·메시지는 응답에 넣지 않습니다(`refunds.failure_code`에만 기록). 결제(`payments.status`)는
승인 기록이라 `DONE`으로 남고, 환불은 `refunds`에서 확인합니다. 환불된 주문에 결제를 다시 시작하면 409
`ORDER_NOT_PAYABLE`입니다.

## 환불 결과 재확인 작업

```sh
uv run --directory apps/api python -m aura_api.infra.reconcile_refunds [--older-than 120] [--limit 100]
```

`IN_PROGRESS` 환불을 **원래 멱등키**로 다시 요청해 결과를 반영합니다(`checked/done/failed/pending` 출력,
`pending`이 있으면 종료 코드 1). 토스 멱등키는 15일간 유효하며, 그 뒤에는 `ALREADY_CANCELED_PAYMENT` →
결제 조회 경로로 같은 결과를 확인합니다. 스케줄러는 등록하지 않았습니다. `review_reason`이 있는 환불은
작업이 반복해도 `pending`이므로 사람이 PG 대시보드와 대조해야 합니다.

## 마이그레이션 0009

- `refunds` 테이블(환불 시도별 1행): 금액(결제 금액 복사)·사유·요청자(주문 이력에 그대로 기록)·상태
  (`IN_PROGRESS`/`DONE`/`FAILED`)·PG `transactionKey`·실패 코드·`review_reason`.
- 되돌리면 `refunds` 테이블이 **삭제**됩니다. 환불이 PG를 통해 돌려준 돈의 유일한 기록이므로 운영에서는 먼저
  백업하고 `SELECT * FROM refunds`를 별도로 보관한 뒤 실행합니다. 되돌린 뒤 `cancelled`로 남은 주문과 상태
  이력은 유지됩니다.

## 검증

- Fake PG와 격리 PostgreSQL(17): 전액 환불의 주문·이력·재고·쿠폰 일치, 중복·동시 환불, PG 불가·응답 유실·
  기록 중 DB 오류 뒤 재전송과 재확인 작업, 확정 거절 뒤 재시도, 금액 불일치 검토, 환불 중 상태 변경 차단,
  준비 중 이후 거절, 소유자·인증, PG 미설정, **PG 호출 중 DB 행 잠금이 없음**(별도 연결의 `FOR UPDATE NOWAIT`).
- 토스 클라이언트 단위 테스트: 요청 형식(경로·인증·멱등키·`cancelAmount` 없음), 환불 완료 판정, 부분·불일치
  취소, `ALREADY_CANCELED_PAYMENT` 조회, 확정 거절과 결과 불명 구분.
- 실제 토스 **테스트** 환경(2026-10-27, 일회용 DB·로컬 서버): 결제위젯으로 승인한 31,000원(계좌이체) 결제를
  환불해 토스 `CANCELED`·취소 1건(31,000원)과 우리 기록(`refund DONE`, 주문 `cancelled`, 이력)이 일치함을
  확인했습니다. 같은 요청 재전송은 200이고 환불 행·토스 취소 모두 늘지 않았습니다. 같은 멱등키 재요청과
  다른 멱등키 재요청(`ALREADY_CANCELED_PAYMENT`)은 모두 같은 `transactionKey`를 돌려주고 취소는 1건으로
  유지됐습니다. 존재하지 않는 결제 취소는 `NOT_FOUND_PAYMENT` 확정 거절로 매핑됐습니다.

실제 토스에서는 타임아웃·응답 유실·동시 환불·가상계좌·부분 환불·운영 키를 재현하지 않았고, 그 부분은 Fake PG
테스트로만 검증했습니다.
