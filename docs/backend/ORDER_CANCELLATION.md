# 미결제 주문 취소와 재고·쿠폰 복구 (마이그레이션 0008)

주문 접수 시 재고 차감과 쿠폰 사용이 이미 끝나므로, 결제하지 않은 주문이 재고와 쿠폰을 무기한
점유하지 않도록 회원 취소와 미결제 만료 작업을 추가했습니다. 결제가 끝난 주문의 취소는 PG 환불이
먼저 필요하므로 [환불 문서](REFUNDS.md)(0009)에서 다룹니다.

## 취소 대상과 결과

| 주문·결제 상태                         | 회원 취소 / 만료 작업                                                 |
| -------------------------------------- | --------------------------------------------------------------------- |
| `received`, 결제 시도 없음             | 취소                                                                  |
| `received`, 결제 대기 `READY`          | 취소 + 결제 시도 `CANCELED` (PG 승인 요청 전)                         |
| `received`, 결제 확인 중 `IN_PROGRESS` | 거절 409 `PAYMENT_IN_PROGRESS` / 만료 작업은 건너뜀                   |
| `paid`                                 | 회원 취소는 PG 전액 환불 뒤 취소([환불](REFUNDS.md)) / 만료 대상 아님 |
| `preparing` 이후                       | 거절 409 `ORDER_NOT_CANCELLABLE` / 만료 대상 아님                     |
| `cancelled`                            | 회원 취소는 그대로 200, 아무것도 다시 되돌리지 않음                   |

결제 확인 중인 주문은 PG가 승인하고 있을 수 있으므로 절대 취소하지 않습니다. 결과 재확인 작업
(`reconcile_payments`)으로 결과를 확정한 뒤 다시 판단합니다.

## 한 트랜잭션에서 바뀌는 것

1. 주문 행을 잠급니다(회원 취소는 활성 회원·본인 주문 조건 포함). 결제 생성·승인 기록과 같은 잠금입니다.
2. 결제 시도를 확인합니다. `IN_PROGRESS`·`DONE`이면 중단하고, `READY`면 `CANCELED`로 닫습니다.
3. `change_status()`로 `cancelled`와 이력(회원: `member`·회원 ID·`member request`, 만료: `system`·
   `unpaid order expired`)을 기록합니다.
4. 쿠폰은 이 주문이 사용한 경우에만(`used_order_id` = 주문) `AVAILABLE`로 되돌립니다.
5. 재고는 주문 접수 때와 같은 규칙으로 되돌립니다. 단품·Gift Set 상품 수량과 Gift Set 구성품 수량을
   더하고, 맞춤 조향은 재고를 쓰지 않았으므로 제외합니다. 상품 ID 순서로 갱신합니다.

중간에 실패하면 전부 롤백됩니다. 쿠폰 → 상품 순서는 주문 접수와 같아 교착을 피합니다.
주문의 `coupon_id`는 기록으로 남고, 되돌린 쿠폰은 새 주문에 다시 쓸 수 있습니다.

## 동시 실행

- 같은 주문 중복 취소: 주문 행 잠금으로 직렬화되고, 두 번째부터는 `cancelled`를 보고 아무것도
  되돌리지 않습니다.
- 취소와 결제 승인: 둘 다 주문 행을 먼저 잠급니다. 승인 요청이 먼저 `IN_PROGRESS`를 잡으면 취소가
  409이고, 취소가 먼저면 결제 시도가 `CANCELED`라 승인 요청이 409 `PAYMENT_CLOSED`입니다. PG 승인은
  확인 단계 이후에만 호출되므로 취소된 주문에 대한 승인은 일어나지 않습니다.
- 만료 작업은 주문마다 트랜잭션을 나누고, 잠근 뒤 상태와 시각을 다시 확인합니다.

## 미결제 만료 작업

```sh
# 대상 수만 확인 (기본)
uv run --directory apps/api python -m aura_api.infra.expire_unpaid_orders --ttl-minutes <정책값>
# 실제 취소
uv run --directory apps/api python -m aura_api.infra.expire_unpaid_orders --execute
```

- 만료 시간은 `AURA_UNPAID_ORDER_TTL_MINUTES`(1~43200분) 또는 `--ttl-minutes`로 받습니다.
  **운영 기본값은 정하지 않았습니다.** 값이 없으면 작업이 실행을 거부합니다.
- 토스 결제 인증 후 승인까지 10분 제한이 있으므로, 정책값은 결제창 체류 시간보다 충분히 길어야 합니다.
- 결제 결과 재확인 작업을 먼저 실행해 `IN_PROGRESS`를 줄인 뒤 만료 작업을 실행하는 순서를 권장합니다.
- 출력의 `due`는 이번 실행의 대상 수(`--limit` 이하)입니다. 더 많은 대상이 남아 있을 수 있습니다.
  `cancelled`·`skipped`는 실행 결과이고, dry run에서는 그 시점의 예상치입니다(결제 확인 중·완료 주문은
  건너뜀으로 셉니다). 실행 직전에 결제가 시작되면 실제 결과와 달라질 수 있습니다.
- 스케줄러는 등록하지 않았습니다.

## API (계약 1.3.0)

`POST /api/v1/orders/{orderId}/cancel` (회원 JWT, CSRF) → 200 `OrderOut`

| 상황                    | 응답                                                         |
| ----------------------- | ------------------------------------------------------------ |
| 취소됨 또는 이미 취소됨 | 200, `status: "cancelled"`                                   |
| 다른 회원·없는 주문     | 404 `ORDER_NOT_FOUND`                                        |
| 결제 확인 중            | 409 `PAYMENT_IN_PROGRESS`                                    |
| 결제 완료(`paid`)       | PG 환불 뒤 200, 확인 중 202 (계약 1.4.0, [환불](REFUNDS.md)) |
| 준비 중 이후 상태       | 409 `ORDER_NOT_CANCELLABLE`                                  |
| 비로그인·관리자 토큰    | 401                                                          |

## 마이그레이션 0008

- `payments.status`에 `CANCELED` 추가. `CANCELED`는 paymentKey 없이 허용되며 주문당 열린 결제 1건
  제약에서 빠집니다.
- `orders (created_at) WHERE status = 'received'` 부분 인덱스.
- 되돌리기는 `CANCELED` 결제 시도 행을 **삭제**한 뒤 0007 제약으로 돌아갑니다.

### 0008 되돌리기의 데이터 손실

0007 제약은 `READY`가 아닌 시도에 paymentKey를 요구하므로 `CANCELED` 행을 다른 상태로 바꿀 수 없어
삭제합니다. 삭제되는 것은 취소된 주문의 미사용 결제 시도 기록(시도 ID, PG 주문번호, 금액, 발급 시각,
`ORDER_CANCELLED`)입니다. PG에 승인 요청을 보낸 적이 없는 행이라 결제·환불 금액에는 영향이 없고,
주문의 `cancelled` 상태와 상태 변경 이력은 남습니다. 다시 0008을 적용해도 삭제된 행은 복구되지 않습니다.

운영에서 되돌려야 하면 먼저 백업을 확인하고, 필요하면
`SELECT * FROM payments WHERE status = 'CANCELED'` 결과를 별도로 보관한 뒤 실행합니다.

## 남은 것

- 만료 시간 정책값 결정과 만료·재확인 작업의 스케줄 등록
- BFF `POST /api/orders/{id}/cancel`과 주문 내역 화면의 취소 버튼
- 관리자 취소(결제 완료 주문 환불은 0009에서 구현)
- 관리자 대시보드 "최근 7일 주문 수·금액"에 취소 주문을 포함할지 결정(현재 포함)
- 회원 탈퇴 예약 삭제는 주문이 참조하는 쿠폰을 보존하므로, 되돌린 쿠폰도 취소 주문과 함께 남습니다.
