# FastAPI 공통 요청 처리 — CRA-8

후속 보안 작업의 CSRF 검사·보안 헤더·현재 미들웨어 순서는
[CSRF·XSS 공통 보안](SECURITY_CSRF_XSS.md)을 참고합니다. 아래 내용과 57개 테스트 결과는
CRA-8 최초 구현 시점의 기록입니다.

이 문서는 AURA 백엔드의 **공통 요청 ID 및 예외 처리 모듈** 최초 구현과 검증 결과를 정리합니다.

- **담당자:** 전예진
- **Linear 이슈:** [CRA-8](https://linear.app/crasnec/issue/CRA-8)
- **작업 브랜치:** `feature/backend-core-yejin`
- **PR 대상 브랜치:** `develop`
- **검증일:** 2026-10-26
- **기준 문서:** [FastAPI BFF 계약](../FASTAPI_BFF.md)

## 1. 목적과 주요 용어

공통 모듈은 여러 API에서 반복하는 작업을 한곳에서 처리하는 기능입니다. 이번 구현에서는 요청마다 추적 번호를 부여하고, 오류가 발생하면 내부 정보를 숨긴 일관된 응답을 반환하도록 구성했습니다.

| 용어              | 읽는 법          | 설명                                                           |
| ----------------- | ---------------- | -------------------------------------------------------------- |
| FastAPI           | 패스트에이피아이 | Python으로 HTTP API를 만드는 프레임워크                        |
| Starlette         | 스타렛           | FastAPI의 요청·응답·오류 처리 기반                             |
| Middleware        | 미들웨어         | 요청이 들어오고 응답이 나가는 사이에 공통 작업을 처리하는 기능 |
| Exception handler | 익셉션 핸들러    | 오류를 적절한 HTTP 응답으로 바꾸는 함수                        |
| UUID              | 유유아이디       | 요청을 구분하기 위한 고유 식별자                               |
| ASGI              | 에이에스지아이   | Python 웹 서버와 애플리케이션 간 통신 규약                     |
| BFF               | 비에프에프       | 프론트엔드와 업무 백엔드 사이에서 요청을 중계하는 계층         |
| Request ID        | 리퀘스트 아이디  | 요청 추적을 위한 접수 번호                                     |

요청 ID는 식당의 **접수 번호**와 비슷합니다. 요청이 여러 서버를 지나갈 때 같은 요청을 추적하는 데 쓰지만, 사용자 신원이나 접근 권한을 증명하지는 않습니다.

## 3. 실제 요청 처리 흐름

서버 시작 시 `main.py`의 `app = create_app()`이 설정을 읽고 라우터 및 공통 처리 기능을 연결합니다. **요청이 들어올 때마다 앱 전체를 새로 생성하는 구조는 아닙니다.**

```text
브라우저
  → Next.js BFF
    → FastAPI (Uvicorn)
      → ServerErrorMiddleware: 예상하지 못한 서버 오류 처리
        → RequestIDMiddleware: 요청 ID 확인·생성 및 저장
          → ExceptionMiddleware: 처리 가능한 HTTP 예외·요청 검증 오류 처리
            → 라우터 → API 함수 → 응답
```

- **라우터**는 어떤 API 함수가 요청을 처리할지 결정합니다.
- **요청 ID 미들웨어**는 요청 전후에 동작하며 추적 번호를 관리합니다.
- **예외 처리기**는 오류가 발생한 경우 HTTP 상태와 안전한 오류 메시지를 결정합니다.

정상 응답 및 처리된 HTTP 오류 응답에는 요청 ID 미들웨어가 `X-Request-ID` 헤더를 붙입니다.

### 3.1 예상하지 못한 500 오류 처리

일반적인 미들웨어의 응답 경로와 달리, `ServerErrorMiddleware`가 만든 500 응답은 요청 ID 미들웨어를 다시 지나지 않을 수 있습니다. 따라서 `server_exception_handler()`가 `X-Request-ID` 응답 헤더를 직접 설정합니다.

1. 먼저 `request.state.request_id`에 유효한 요청 ID가 있는지 확인합니다.
2. ID가 없거나 올바르지 않다면 원래 요청의 `X-Request-ID` 헤더가 유효한 UUID 하나인지 확인합니다.
3. 유효한 ID가 정확히 하나라면 해당 값을 유지합니다.
4. 헤더가 없거나 유효하지 않으면 `uuid4()`로 새 요청 ID를 만듭니다.
5. 내부 예외 내용은 공개하지 않고, 안전한 500 JSON 본문과 요청 ID 헤더를 반환합니다.

이 보완은 **요청 ID 미들웨어가 실행되기 전에 오류가 발생하는 상황**에서 예외 처리기까지 다시 실패하는 것을 방지하기 위한 것입니다. 관련 상황 3가지를 테스트에 추가했습니다.

미들웨어를 새로 등록할 때는 실행 순서가 달라질 수 있으므로 이 테스트를 유지해야 합니다.

## 4. 공통 오류 응답

오류 응답은 아래 형식으로 통일합니다.

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "입력 항목을 확인해 주세요."
  }
}
```

주요 동작은 다음과 같습니다.

| 상황                      | HTTP 상태 | 오류 코드          | 공개 메시지                     |
| ------------------------- | --------- | ------------------ | ------------------------------- |
| `GET /health` 정상 응답   | 200       | 해당 없음          | `{"status":"ok"}`               |
| 존재하지 않는 경로        | 404       | `HTTP_404`         | 요청한 경로를 찾을 수 없습니다. |
| 허용하지 않는 HTTP 메서드 | 405       | `HTTP_405`         | 지원하지 않는 요청 방식입니다.  |
| 입력값 검증 실패          | 422       | `VALIDATION_ERROR` | 입력 항목을 확인해 주세요.      |
| 예상하지 못한 서버 오류   | 500       | `INTERNAL_ERROR`   | 요청을 처리하지 못했어요.       |

500 오류의 JSON 예시는 다음과 같습니다.

```json
{
  "error": {
    "code": "INTERNAL_ERROR",
    "message": "요청을 처리하지 못했어요."
  }
}
```

기타 `HTTPException`도 원래 HTTP 상태 코드를 유지합니다. 오류 코드는 422이면 `VALIDATION_ERROR`, 5xx이면 `INTERNAL_ERROR`, 그 외에는 `HTTP_상태번호`를 사용합니다. 예를 들어 503 응답의 오류 코드가 `INTERNAL_ERROR`여도 실제 HTTP 상태는 **503**으로 유지합니다.

정상적인 `GET /health` 및 `GET /api/v1/health`의 상태 코드와 응답은 기존과 동일합니다. 422·500 오류는 현재 운영 API에서 재현할 업무 경로가 없으므로 자동 테스트 안에서만 만든 테스트용 경로를 사용했습니다. `/test/*` 경로는 운영 앱에 추가하지 않았습니다.

## 5. 요청 ID와 BFF의 관계

- BFF는 브라우저가 전달한 요청 ID를 그대로 신뢰하지 않고 새로운 UUID를 만듭니다.
- FastAPI는 전달된 `X-Request-ID`가 **하이픈 포함 36자리 UUID 형식**에 맞으면 값을 유지합니다. 대문자 16진수도 허용하며 특정 UUID 버전으로 제한하지 않습니다.
- 헤더가 없거나 비어 있거나, 길이·문자 형식이 잘못됐거나, 요청 ID 헤더가 중복되어 있으면 새 UUID v4를 생성합니다.
- 요청 ID는 각 요청의 ASGI `scope`에 포함된 `state`에 저장합니다. 전역 변수에 저장하지 않아 동시 요청 간 값이 섞이지 않도록 합니다.
- BFF가 생성한 유효한 ID를 유지하면 웹 요청과 FastAPI 요청을 같은 번호로 연결하여 추적할 수 있습니다.
- **UUID 형식이 유효하다는 사실 자체는 신원 인증이나 BFF 발신 증명이 아닙니다.**

현재 BFF는 백엔드의 `error.message`를 참고하지만 `error.code`를 그대로 전달하지는 않습니다. BFF의 기존 변환 정책에 따라 422는 `VALIDATION_ERROR`, 기타 4xx는 `HTTP_상태번호`로 처리하고, FastAPI의 5xx는 브라우저에서 502로 전달될 수 있습니다. 따라서 **FastAPI 직접 응답의 500과 브라우저가 받은 502는 구분**해야 합니다.

이번 작업에서는 BFF의 코드와 공개 계약을 변경하지 않았습니다.

## 6. 민감정보 보호 및 한계

### 6.1 이번 구현에 포함된 보호

- `HTTPException.detail`에 문자열이나 객체가 있어도 그대로 클라이언트에 반환하지 않고, 상태 코드에 맞는 고정 메시지를 사용합니다.
- 422 응답에는 원본 입력값·비밀번호·검증 상세를 포함하지 않습니다.
- 500 응답에는 내부 예외 문자열·토큰·DB 주소 등을 포함하지 않습니다.
- 예외 헤더는 `Allow`, `WWW-Authenticate`, `Retry-After`처럼 허용된 표준 헤더만 전달합니다.
- 임의의 내부 디버그 헤더 및 `Set-Cookie`는 자동 복사하지 않습니다.
- 새 요청 본문·쿠키·토큰 기록용 로그는 추가하지 않았습니다.
- 기존 `debug=False` 동작을 유지합니다.

### 6.2 아직 해결되지 않은 사항

- 허용 목록에 있는 표준 헤더라도 **헤더 값 자체에 민감정보를 넣어서는 안 됩니다.**
- 서버가 실제 예외를 기록하는 Uvicorn·프록시·관측 도구 로그는 별도 보안 정책이 필요합니다. 이 모듈만으로 모든 서버 로그가 보호되는 것은 아닙니다.
- 운영에서 `debug=True`를 사용하면 예외의 상세 호출 기록(traceback)이 외부에 노출될 수 있으므로 사용하지 않아야 합니다.
- 이미 응답 전송이 시작된 스트리밍 응답이나 백그라운드 작업 오류는 응답 상태와 본문을 안전한 500 형태로 바꾸지 못할 수 있습니다.
- 향후 인증 처리에서 세션 만료 시 쿠키 삭제 등이 필요하다면 관련 헤더 정책을 별도로 설계해야 합니다.

### 7.3 주요 검증 항목

- 정상·누락·잘못된·중복 요청 ID 처리
- 정상 UUID 유지 및 잘못된 ID 교체
- 200·404·405·422·500 응답의 요청 ID 헤더 확인
- 미들웨어에서 ID를 저장하기 전에 발생한 500 오류 대응
- 16개 동시 요청의 요청 ID 분리
- HTTP 예외 상태 코드 유지
- `Allow`, `WWW-Authenticate`, `Retry-After` 등 허용 헤더 보존
- 비밀번호·토큰·DB 주소 등의 민감정보 비노출
- 서버 응답 모델 검증 실패 시 안전한 500 응답
- 기존 OpenAPI 경로 및 설정 동작 유지

추가한 500 오류 보완 테스트는 **요청 ID가 없는 경우, 잘못된 ID가 있는 경우, 유효한 ID가 있는 경우**의 세 가지 상황을 검증합니다. 세 경우 모두 안전한 JSON 오류 응답과 유효한 요청 ID 헤더를 확인합니다.

### 7.4 검증 범위 밖의 사항

실제 Next.js BFF와 FastAPI를 함께 실행하는 **통합 테스트는 이번 검증에 포함하지 않았습니다.**

추가로 시도했던 `npm run check`는 당시 Prettier 실행 파일을 찾지 못해 중단되었고, `npm run build`는 웹의 `@tanstack/react-query` 의존성을 찾지 못해 실패했습니다. 해당 결과만으로 소스 자체의 문제를 확정할 수는 없으며, 이번 CRA-8 API 구현 범위에서 웹 의존성을 변경하지 않았습니다.

따라서 이번에 **검증 완료된 범위는 `npm run check:api`와 그 하위 API 검사·테스트**입니다. 전체 웹 빌드 성공을 의미하지는 않습니다.

| **정다라** | PostgreSQL, Alembic, CI, 배포 등 초기 인프라 및 서버 로그 정책 |
| **심우섭** | 회원·상품·주문 모델 및 도메인 업무 규칙                        |

### 8.3 후속 협의 사항

- FastAPI에 외부에서 직접 접근하도록 허용할지 여부
- 요청 본문 크기 및 빈도 제한을 적용할 위치
- 서버 예외 로그의 민감정보 보호·보존·접근 정책
- 업무별 공개 오류 메시지 기준
- 인증 실패 시 `WWW-Authenticate` 및 세션 쿠키 처리 정책
- OpenAPI 공통 오류 응답 스키마 등록 여부

현재 BFF에서 처리하는 **32KiB 본문 제한 및 출처 검사**를 이번 FastAPI 구현에서 중복 구현하지 않았습니다. 추후 직접 API 접근 정책이 확정되면 보안 범위를 다시 검토해야 합니다.
