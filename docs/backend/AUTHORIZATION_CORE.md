# AURA JWT 공통 인증·인가 기반

## 1. 현재 구현과 전환 범위

후속 로그인·발급·Refresh 회전·로그아웃 API와 PostgreSQL 저장소 코드의 현재 상태는
[JWT 생명주기](JWT_LIFECYCLE.md)에 정리했습니다. 실제 스키마·DB·BFF 연결은 아직 대기 중입니다.

인증(Authentication, 오센티케이션)은 “누구인가?”, 인가(Authorization, 오서라이제이션)는
“이 작업을 해도 되는가?”를 확인합니다. 예를 들어 검증된 토큰으로 사용자를 확인한 뒤,
조회하려는 자료의 서버 측 소유자가 같은 사람인지 검사합니다.

FastAPI 공통 인증을 세션 확인 인터페이스에서 JWT(JSON Web Token, 제이더블유티) 검증으로
전환했습니다. `SessionVerifier`, `RejectAllSessions`, 세션 쿠키 이름 설정은 제거했습니다.
`AuthenticatedUser`, `CurrentUser`, 권한 검사와 소유권 검사 인터페이스는 유지합니다.

**JWT 검증 설정이 없으면 인증이 필요한 요청은 모두 401입니다.**
JWT 설정이 유효해도 폐기 저장소가 연결되지 않으면 401입니다. 저장소 미연결을
“빈 블랙리스트”로 해석하지 않습니다.
헬스 API는 공개 상태입니다. PR #31은 검증 기반을 구현했으며, 후속 생명주기 작업에서
로그인·토큰 발급·Refresh·로그아웃과 DB 어댑터 코드를 추가했습니다. 회원가입·실제 DB 검증은 미완료입니다.

## 3. JWT 검증 정책

FastAPI는 정확히 한 개의 `Authorization: Bearer <JWT>` 헤더를 받습니다.
Bearer(베어러)는 토큰 전달 방식이며 헤더의 scheme은 대소문자를 구분하지 않습니다.
중복 헤더, 빈 토큰, 잘못된 형식, 8192자 초과 토큰은 401입니다.
쿠키·쿼리·`X-User-ID`·`X-Session-Owner`·`X-Request-ID`·`X-Aura-BFF-Key`로 인증하지 않습니다.

검증 라이브러리는 PyJWT이며 잠금 파일의 버전을 사용합니다.
검증할 알고리즘은 토큰의 `alg`가 아닌 서버 설정에서 가져옵니다.
이번 구현은 **HS256 하나만 지원**하며 HS512·RS256·`alg=none` 등은 거절합니다.
HS256은 같은 비밀키로 서명과 검증을 수행합니다. 다른 알고리즘·공개키·JWKS·키 회전 지원은
발급자 계약을 정한 뒤 별도로 구현해야 하며, 이번에 여러 알고리즘을 혼용하지 않습니다.

필수 claim(클레임, 토큰의 정보 항목)은 다음과 같습니다.

- `exp`: 만료 시각. 유효기간이 지난 토큰은 거절합니다. 유한한 숫자만 허용하고
  문자열·불리언·무한대는 거절합니다. 별도 시간 유예는 두지 않습니다.
- `iss`: issuer(이슈어, 발급자). 설정값과 정확히 같아야 합니다.
- `aud`: audience(오디언스, 사용 대상). 이번 계약은 단일 문자열이며 설정값과 정확히
  같아야 합니다. 배열 audience는 허용하지 않습니다.
- `sub`: subject(서브젝트, 사용자 식별자). 비어 있거나 공백뿐인 값, 문자열이 아닌 값은
  거절합니다. 검증이 끝난 이 값으로만 `AuthenticatedUser.user_id`를 구성합니다.
- `jti`: JWT ID(제이더블유티 아이디, 토큰 고유번호). 비어 있거나 공백뿐인 값,
  문자열이 아닌 값은 거절합니다. 형식은 UUID로 제한하지 않으며 발급자가 중복 없이 생성해야 합니다.
- `iat`: issued at(이슈드 앳, 발급 시각). 필수 유한 숫자이며 문자열·불리언·음수·미래 시각은
  거절합니다. `exp`는 `iat`보다 커야 합니다. 최대 수명은 이번에 임의로 확정하지 않았습니다.

선택 항목 `nbf`가 있으면 사용 가능 시각 검사와 숫자 형식 검사도 적용합니다.
서명·등록 클레임 검증이 완료되기 전에는 사용자나 권한을 구성하지 않습니다.
토큰 헤더의 URL·키 정보로 외부 키를 조회하지 않습니다.

검증된 토큰의 선택 항목 `permissions`는 비어 있지 않은 문자열들의 배열입니다.
항목 자체를 생략하면 권한은 빈 집합입니다. 문자열 하나·숫자·빈 권한명 등 잘못된 자료형은
401이며 권한을 추측하거나 관리자 권한을 추가하지 않습니다.
`permissions`의 이름·발급 규칙은 팀 합의가 필요하며 예제의 `example:read` 등은 업무 정책이 아닙니다.
JWT는 암호화된 사용자 정보가 아니므로 토큰 내용에 비밀번호·비밀키·민감정보를 넣으면 안 됩니다.
설계서 기준으로 이름·이메일·비밀번호는 발급할 JWT에 포함하지 않습니다. 발급 API가 없으므로
실제 발급 payload의 개인정보 배제는 아직 검증하지 못했습니다. 후속 발급 구현에서 허용 필드를
명시해야 하며, 현재 검증기는 토큰 원문이나 알 수 없는 claim을 응답으로 반환하지 않습니다.

### 폐기 조회와 기본 거부

이 보완은 사용자가 전달한 `AURA_SELECT_백엔드_설계서_통합본.md` 5장
인증·인가 핵심 요구사항(NFR-03~05 / FR-AUTH)을 기준으로 합니다.
Refresh Token 자동 갱신은 선택 기능이며 jti 블랙리스트와 로그아웃 후 차단은 필수입니다.

`TokenRevocationStore`의 연결 규약은 다음과 같습니다.

```python
async def is_revoked(self, *, issuer: str, jti: str) -> bool:
    ...
```

서명·필수 정보·형식 검증을 통과한 `iss`와 `jti`만 이 함수에 전달합니다.
`True`는 폐기, `False`는 조회에 성공했고 폐기되지 않았음을 뜻합니다.
조회 예외·타임아웃·미연결·잘못된 반환값은 인증 거절이며, **명시적인 bool `False`만 허용**합니다.
`None`, `0`, 빈 목록, 문자열 `"false"`를 정상 조회로 간주하지 않습니다.
취소 같은 시스템 제어 예외까지 삼키지는 않습니다.

provider인 `get_token_revocation_store()`는 앱의 인증 저장소를 반환합니다.
DB URL 미설정 시 `UnavailableAuthRepository`가 조회 불가 예외를 발생시키며 인증 계층은 401로 바꿉니다.
명시적인 DB URL 설정 시 PostgreSQL 어댑터를 사용합니다. 스키마·실제 DB 검증 전에는 운영 연결 완료로 보지 않습니다.
가용성보다 안전을 우선하므로 폐기 저장소 장애 시에도 보호 API의 인증이 차단됩니다.

테스트에서만 저장소 대역을 테스트 앱의 `dependency_overrides`에 주입합니다.
JWT 서명 검증 자체는 대체하지 않습니다. 운영 앱에는 메모리 블랙리스트나
미폐기 토큰을 무조건 허용하는 저장소를 등록하지 않습니다.
인증 결과나 미폐기 조회를 전역 캐시에 보관하지 않고 매 요청 다시 조회합니다.

PostgreSQL 어댑터 코드는 `revoked_tokens.jti` 및 발급 계열·활성 상태를 조회합니다. 인터페이스는 발급자도
전달하므로 단일 발급자·jti 전역 유일성 또는 복수 발급자 이름공간 정책을 DB 담당자와 맞춰야 합니다.
운영 테이블·인덱스·마이그레이션은 변경하지 않았습니다. CRA-14 검토용 컬럼 계약과 테스트 SQL만 준비했습니다.
로그아웃 API는 검증된 토큰의 jti를 exp까지 유지되는 폐기 목록에 기록하고 기록 성공을 확인한 뒤
로그아웃을 완료해야 합니다. **쿠키 삭제만으로 로그아웃 완료로 처리하면 안 됩니다.**
저장 실패 처리, 만료 레코드 정리와 동시 요청의 경계도 실제 DB·로그아웃 구현에서 검증해야 합니다.

### 서버 설정

```dotenv
# 네 항목을 모두 설정해야 JWT 인증을 사용할 수 있습니다.
AURA_JWT_ALGORITHM=HS256
# AURA_JWT_SIGNING_KEY=<별도로 생성·관리하는 무작위 비밀키>
AURA_JWT_ISSUER=https://issuer.example.com
AURA_JWT_AUDIENCE=aura-api
```

기본값은 모두 미설정이며 코드에 개발용 비밀키는 없습니다. 일부만 설정하거나 잘못된
알고리즘·빈 issuer/audience를 지정하면 앱 설정 단계에서 실패합니다.
비밀키는 32~128자의 URL-safe ASCII 값만 허용합니다. 실제로는 암호학적으로 안전한
난수로 생성하고 TLS·비밀값 저장소·주입·회전을 관리해야 합니다. 길이 검사는 난수의 품질을
보장하지 않습니다. BFF 공유 키와 다른 값을 사용하고 Git·응답·로그에 기록하지 않습니다.
키는 SecretStr로 보관하며 설정 오류 문자열에도 입력값을 숨깁니다.
`AURA_SESSION_COOKIE_NAME`은 더 이상 FastAPI 인증 설정으로 사용하지 않습니다.

## 4. 인가와 응답

인증만 필요한 함수는 `user: CurrentUser`를 사용합니다.
권한이 필요하면 `Depends(require_permissions("권한1", "권한2"))`로 모두 필요한 권한을 선언합니다.
도메인 코드가 자료를 조회한 뒤 `ensure_resource_owner(user, resource.owner_user_id)`를 호출합니다.
소유자 ID를 클라이언트 본문·쿼리·헤더에서 가져오면 안 됩니다.
Dependency를 선언하지 않은 새 경로가 자동으로 보호되는 것은 아닙니다.

- 401: 토큰 누락·서명 실패·만료·필수 정보 오류·미설정 검증기·폐기 또는 폐기 조회 불가.
  기존 `HTTP_401`과 “인증이 필요합니다.”를 반환하고 `WWW-Authenticate: Bearer`를 포함합니다.
- 403: 인증은 됐지만 권한 또는 소유권이 없습니다. 기존 `HTTP_403`과 고정 안내를 유지합니다.
- 409: 계정 전환 중 요청의 충돌이라는 기존 BFF 계약을 유지합니다. 이번 작업에서는
  `X-Session-Owner`를 신원으로 사용하거나 새로운 409 검사를 구현하지 않습니다.

정상·401·403 응답에도 요청 ID가 유지됩니다. 토큰·키·검증 예외 상세를 응답으로 반환하지
않으며 새 로깅도 추가하지 않았습니다.

```text
기본 서버 오류 계층 → 요청 ID → 기존 CSRF → 공통 예외 처리
  → JWT 서명·필수 클레임 검증 → 폐기 조회 → 사용자 구성
    → 권한 검사 → 서버의 자료 조회·소유권 검사 → 업무 처리
```

JWT가 유효해도 기존 CSRF를 우회하지 못합니다. 출처가 잘못된 변경 요청은 인증 전에 403일
수 있습니다. 출처 없는 BFF 변경 요청은 기존 서버 공유 키가 필요하고 JWT도 따로 필요합니다.

## 5. BFF JWT 연결

Next.js BFF는 기본 `API_AUTH_MODE=cookie`로 기존 Mock의 불투명 세션 쿠키를 전달합니다.
FastAPI용 `API_AUTH_MODE=jwt`에서는 `API_SESSION_COOKIE`의 JWT만 꺼내
`Authorization: Bearer <JWT>`로 전송합니다. 브라우저의 Authorization과 사용자 ID는 복사하지
않고, 백엔드 Cookie도 보내지 않습니다. 공개 카탈로그와 공용 RSC는 사용자 인증을 전달하지 않습니다.
FastAPI는 계속 Bearer만 검증하며 쿠키를 직접 읽는 대체 인증은 제공하지 않습니다.

현재 BFF가 기대하는 발급 계약은 기존 `Session` JSON과 `Set-Cookie: aura_session=<JWT>`입니다.
생명주기 API는 TokenPair JSON을 반환하며 쿠키를 발급하지 않습니다. 로그아웃도 204이므로
BFF의 Session 응답 처리와 아직 연결되지 않았습니다. 응답 변환·익명 방문자 정책 합의가 필요합니다.
BFF가 Path·HttpOnly·SameSite·HTTPS의 Secure를 적용하고 발급자의 수명 속성을 보존합니다.
BFF는 JWT 형식·3,800자 전송 상한만 확인하며 서명·클레임·폐기 검증은 위 FastAPI 검증기가
계속 담당합니다. 서명키는 BFF에 주입하지 않고 토큰은 localStorage에 저장하지 않습니다.
인증 JSON은 공개 `Session`·`Member` 필드로 제한하고 추가 토큰·비밀번호 필드는 제거합니다.

BFF의 401은 토큰 쿠키 삭제와 고정 `WWW-Authenticate: Bearer`를 반환합니다.
403·409·백엔드 장애에서는 기존 쿠키를 유지합니다. 로그아웃은 토큰을 백엔드로 전송하고
폐기 완료 응답을 기다립니다. 쿠키만 삭제하고 성공을 반환하거나 쓰기 요청을 재시도하지 않습니다.
출처 검사·본문 제한·BFF 공유 키·요청 ID·공개 오류 형식은 유지합니다.

`npm run test:e2e:jwt`는 실제 Next 프로덕션 서버와 테스트 전용 FastAPI 앱을 함께 실행합니다.
FastAPI 공통 검증기·CSRF·오류 처리를 그대로 사용하며 정상·만료·위조·회원 분리·폐기 후
재접근 차단을 검사합니다. 해당 앱의 발급과 메모리 폐기 저장소는 테스트 전용입니다.
별도로 운영 앱의 로그인·Refresh 회전·로그아웃 API와 PostgreSQL 어댑터 코드가 추가됐습니다.
인증 확장 스키마 합의·실제 DB 검증·BFF 응답 연결은 대기 중이며 헬스·테스트 성공이 운영 연결 완료를 뜻하지 않습니다.
익명 방문자의 `guestId`를 담은 토큰의 발급·검증, 로그인·로그아웃 중 guestId 보존은
업무 API가 구현해야 합니다. 회원용 `CurrentUser`가 익명 토큰을 허용하지 않도록 구별 정책도 필요합니다.

세부 경계·환경 설정·로그아웃과 401 정책은 [BFF 계약](../FASTAPI_BFF.md)을 참고합니다.

## 7. 제한과 후속 합의

- 후속 생명주기 작업의 로그인·발급·Refresh·로그아웃·DB 어댑터 구현 및 최신 테스트는
  [JWT 생명주기](JWT_LIFECYCLE.md)를 참고합니다. 회원가입·BFF·실제 DB 연결은 대기 중입니다.
- 검증된 sub가 실제 활성 회원인지 확인하는 DB 조회, 즉시 계정 정지·권한 변경 반영,
  실제 PostgreSQL 폐기 기록 검증·키 회전은 미완료입니다.
  폐기 조회·로그아웃 트랜잭션 코드는 추가했지만 운영 DB까지 연결된 것은 아닙니다.
  DB 미설정·조회 실패 시에는 보호 API가 인증을 거부합니다.
- Access Token 15분·Refresh Token 7일은 생명주기 구현의 변경 가능한 기본값이며 운영 확정값은 아닙니다.
  Refresh 발급·회전은 후속 요청의 필수 범위로 구현했고, BFF 자동 갱신은 아직 구현하지 않았습니다.
- 발급자와 알고리즘, issuer·audience·sub 형식, permissions 이름·버전·토큰 수명과
  여러 종류 토큰의 구별 규칙은 팀 합의가 필요합니다. 이번 검증기는 지정한 단일 발급자·대상만 받습니다.
  발급자는 API용 audience를 액세스 토큰에만 사용해야 하며 Refresh Token 등과 공유하면 안 됩니다.
- 우섭님: 사용자 식별자·업무별 권한·자료 소유자 조회·관리자 예외·존재 은닉 정책을 합의합니다.
- 다라님: JWT 키 생성·안전한 주입·TLS·회전과 로그의 Authorization 마스킹을 합의합니다.
  DB·Alembic·배포 설정은 수정하지 않았습니다.
- BFF 담당자: 확정한 쿠키·401 계약에 업무 API 발급·로그아웃을 연결하고 운영 환경에서 재검증합니다. Refresh Token·회전·탈취 대응은 후속 합의 사항입니다.
