## 1. 배경과 현황

인수한 웹은 Next.js BFF와 Mock API로 정리되어 있다. 브라우저는 같은 출처 `/api`만 호출하고, BFF Route Handler가 백엔드로 연결한다. 지금 백엔드 자리에는 Mock(Express, JSON 파일 저장)이 있다.

FastAPI(`apps/api`)에 준비된 것:

## 3. 기능 요구사항

**우선순위:** P0 = 핵심 화면 흐름에 꼭 필요 / P1 = 연결 완성도 / P2 = 여유가 있을 때. 경로는 BFF 공개 경로이며 FastAPI에서는 `/api`가 `API_PREFIX`(`/api/v1`)로 바뀐다.

### 3.1 상품 (CAT)

| ID        | 우선 | 경로                             | 요구사항 · 인수 기준                                                                                 |
| --------- | ---- | -------------------------------- | ---------------------------------------------------------------------------------------------------- |
| FR-CAT-01 | P0   | `GET /api/catalog`               | `Catalog`(상품 30·컬렉션 3·유형 10·향료 24·향 계열·추천 이름·홈 콘텐츠) 반환. Mock과 같은 값·원본 ID |
| FR-CAT-02 | P0   | `GET /api/catalog/products/{id}` | 상품 1개 반환, 없는 ID는 404. 기존 별칭 ID(`bergamot-veil` 등)도 Mock과 같이 처리                    |
| FR-CAT-03 | P0   | —                                | 가격이 정해지지 않은 상품은 `price: null`. 임의 가격을 만들지 않음                                   |
| FR-CAT-04 | P1   | —                                | 상품 재고를 제공하고 주문 시 서버 재고로 판단                                                        |

### 3.2 회원 · 인증 (AUTH)

| ID         | 우선 | 경로                             | 요구사항 · 인수 기준                                                                                     |
| ---------- | ---- | -------------------------------- | -------------------------------------------------------------------------------------------------------- |
| FR-AUTH-01 | P0   | `GET /api/session`               | `Session { user: Member \| null, guestId }` 반환. 처음 온 방문자에게도 `guestId`와 익명 토큰 발급        |
| FR-AUTH-02 | P0   | `POST /api/auth/register`        | `{ name, email, password, marketing? }` → 201 `Session`. 가입과 동시에 로그인. 같은 이메일은 409         |
| FR-AUTH-03 | P1   | (가입 시)                        | 신규 회원 배송비 쿠폰 1장 발급, 중복 발급 없음. `Member.coupon`으로 보유 여부 표시                       |
| FR-AUTH-04 | P0   | `POST /api/auth/login`           | `{ email, password }` → `Session`. 실패는 401 "이메일 또는 비밀번호를 확인해 주세요." (어느 쪽인지 숨김) |
| FR-AUTH-05 | P0   | `POST /api/auth/logout`          | 본문 없음 → `Session`(user: null, **같은 guestId**). Access Token `jti` 폐기 + Refresh Token 계열 폐기   |
| FR-AUTH-06 | P0   | (모든 회원 경로)                 | 새로고침·새 탭에서도 로그인 유지. 만료·위조·폐기된 토큰은 401(`WWW-Authenticate: Bearer`)                |
| FR-AUTH-07 | P1   | (회원 변경 요청)                 | `X-Session-Owner`가 실제 주인과 다르면 409. 소유권은 이 헤더가 아니라 토큰으로 판단                      |
| FR-AUTH-08 | P0   | (로그인·가입 시)                 | Refresh Token 발급. DB에는 **해시만** 저장하고 만료·사용·폐기 상태를 관리                                |
| FR-AUTH-09 | P0   | 재발급 (FastAPI, 경로 확정 필요) | 유효한 Refresh Token으로 새 Access Token 발급. 쓰인 Refresh Token은 새것으로 **회전**                    |
| FR-AUTH-10 | P0   | (재발급 시)                      | 이미 쓰인 Refresh Token이 다시 오면 탈취로 보고 **같은 계열 전체 폐기**                                  |
| FR-AUTH-11 | P2   | (로그인·요청 시)                 | 정지된 회원 거절(`users.is_active`) — 회원 정지 정책 확정 후                                             |

Refresh Token은 백엔드에서 구현한다. BFF는 아직 Refresh를 연결하지 않으므로(#37) 웹에서는 Access Token 만료 시 다시 로그인한다. BFF 연결은 후속 범위다.

### 3.6 관리자 (ADM)

관리자는 고객과 분리된 `admins` 테이블 계정이며 로그인 API와 쿠키도 따로 쓴다(팀 결정). 업무 경로·DTO는 #32 관리자 API 계약을 따른다.

| ID        | 우선 | 경로                                              | 요구사항 · 인수 기준                                                                         |
| --------- | ---- | ------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| FR-ADM-01 | P0   | `POST /api/admin/auth/login`                      | `{ email, password }` → 관리자 세션. 비활성(`disabled`) 계정·잘못된 비밀번호는 401           |
| FR-ADM-02 | P0   | `POST /api/admin/auth/logout`                     | 관리자 토큰 폐기                                                                             |
| FR-ADM-03 | P0   | `GET /api/admin/session`                          | 현재 관리자 정보 또는 401                                                                    |
| FR-ADM-04 | P1   | `POST /api/admin/admins`                          | 로그인한 관리자만 새 관리자 등록. 같은 이메일은 409. 감사 기록 `admin.create`                |
| FR-ADM-05 | P0   | (모든 `/api/admin/**`)                            | 요청마다 실제 관리자 계정·상태를 다시 조회. 미인증 401, 고객 토큰 403                        |
| FR-ADM-06 | P1   | `GET /api/admin/overview`                         | 최근 7일 주문 수·금액, 문의 상태별 건수, 재고 5개 이하 상품                                  |

| FR-ADM-09 | P0   | `POST /api/admin/products/{id}/stock-adjustments` | `{ version, delta, reason, key }`. 재고 0~99,999 유지, 같은 `key` 재전송은 200(한 번만 반영) |
| FR-ADM-10 | P0   | `GET /api/admin/orders`, `GET .../{id}`           | 기간(한국 시간) 필터 목록, 상세는 주문 당시 스냅샷·주문자·배송지                             |
| FR-ADM-11 | P0   | `GET /api/admin/inquiries`, `GET .../{id}`        | 상태 필터 목록, 상세는 원문·상태·내부 메모·이력                                              |
| FR-ADM-12 | P0   | `PATCH /api/admin/inquiries/{id}`                 | `{ version, status?, memo? }`. `version` 불일치 409. 감사 기록 `inquiry.update`              |
| FR-ADM-13 | P1   | (운영 절차)                                       | 첫 관리자 생성 명령(CLI). 화면 가입 없음                                                     |

## 4. 업무 규칙

업무 규칙의 전체 목록·위반 코드·메시지는 [도메인 규칙](DOMAIN_RULES.md)에 있다. 요약:

| 영역     | 핵심 규칙                                                                                                          | 도메인 규칙 ID |
| -------- | ------------------------------------------------------------------------------------------------------------------ | -------------- |
| 회원     | 이메일 소문자 정규화·중복 금지, 비밀번호 8~256자, 배송비 쿠폰 1회 사용                                             | ID-01~09       |
| 조향     | 있는 향료만, 투입 합계 1~20, 라벨 3종, 레시피는 수정하지 않고 새 버전, 색·비중은 서버 계산                         | AT-01~08       |
| 주문     | 수량 1~15, Gift Set 같은 컬렉션 서로 다른 3개, 가격 미정 주문 불가, 단품+구성품 합산 재고, 5만 원 이상 배송비 무료 | OR-01~15       |
| 입점문의 | 필수 항목·글자 수·이메일 형식·동의(`"on"`)·유형 4종                                                                | PT-01~04       |
| 관리자   | 낙관적 잠금(`version`), 재고 0~99,999, 재고 조정 사유 필수, 변경은 감사 기록                                       | 추가 예정      |

## 5. 비기능 요구사항

| ID     | 분류      | 요구사항                                                                                                                    |
| ------ | --------- | --------------------------------------------------------------------------------------------------------------------------- |
| NFR-01 | 계약      | BFF 계약의 경로·DTO·상태 코드를 지킨다. trailing slash 리다이렉트 없음, 4xx 상태 보존, JSON 응답                            |
| NFR-02 | 구조      | Modular Monolith, 4계층을 계층별 폴더로 분리(`api`·`services`·`domain`·`infra`, 공통 `core`). 도메인은 FastAPI·DB를 모름    |
| NFR-03 | 인증      | JWT 서명·만료·필수 클레임 검증, 로그아웃 토큰 폐기, Refresh Token은 해시 저장·회전, 비밀번호 서버 해시(평문·Mock 해시 금지) |
| NFR-04 | 인가      | 레시피·주문은 토큰의 회원 ID로만 조회·변경. 남의 리소스는 404. 관리자 API는 `admins` 계정으로만                             |
| NFR-05 | 정합성    | 여러 테이블을 바꾸는 작업(가입, 레시피 저장, 주문, 재고 조정)은 하나의 트랜잭션. 재고는 조건부 차감                         |
| NFR-06 | 비밀정보  | JWT 서명키·DB 비밀번호·BFF 공유키는 코드·Git에 넣지 않음(`.env.example`만)                                                  |
| NFR-07 | 로그      | 비밀번호·토큰·개인정보 원문을 로그에 남기지 않음                                                                            |
| NFR-08 | 테스트    | 도메인 단위 테스트, 실제 PostgreSQL 통합 테스트, 계약(BFF) 테스트, `npm run check:api` 통과                                 |
| NFR-09 | 실행      | 문서대로 따라 하면 로컬에서 DB·마이그레이션·시드·API를 띄울 수 있음                                                         |
| NFR-10 | 운영 설계 | 다중 서버 SPOF 대응, TLS·키 회전, 관측(로그·지표·추적), CI/CD 방안을 문서로 제시(실배포 범위 밖)                            |
