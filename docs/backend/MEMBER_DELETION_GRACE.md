# 회원 탈퇴 30일 유예·복구·예약 삭제와 로그인 실패 제한

CRA-34·36 후속 작업입니다. 2026-10-27 확정된 팀 정책을 FastAPI 회원 인증에 반영합니다.
API 계약 요약은 [FastAPI BFF 계약](../FASTAPI_BFF.md), 탈퇴 신청의 토큰 폐기·잠금은
[CRA-34 문서](MEMBER_DEACTIVATION.md)를 함께 봅니다.

> **0010으로 대체됨:** 복구와 자동 삭제는 더 이상 동작하지 않습니다([복구 없는 비활성화](MEMBER_PERMANENT_DEACTIVATION.md)). 아래는 0005~0009 시점의 설계입니다.
>
> **상태:** API·DB 마이그레이션·예약 삭제 명령은 구현됐습니다. 예약 실행 환경(스케줄러)이
> 배포되기 전에는 **30일 후 삭제가 자동으로 일어나지 않습니다.** 이 상태를 완전 삭제 기능 완료로
> 안내하지 않습니다.

## 확정 정책

1. 장바구니는 LocalStorage에 유지하며 백엔드에 저장하지 않습니다.
2. 계정 정지와 회원 탈퇴는 구분하지 않습니다.
3. 탈퇴 신청 후 30일 동안 유예합니다.
4. 30일 이전에 비밀번호로 정상 인증하면 계정을 복구합니다.
5. 복구하지 않고 30일이 지나면 예약 작업으로 개인정보를 삭제합니다.
6. 로그인 실패는 아이디(이메일)별 연속 3회부터 최소 10분 제한합니다.
7. CAPTCHA는 이번 범위가 아닙니다.

## 상태와 시각

`users`에 마이그레이션 0005로 세 컬럼을 추가했습니다. 모든 시각은 DB 시계 기준입니다.

| 상태      | is_active | deletion_requested_at | deletion_scheduled_at | deleted_at |
| --------- | --------- | --------------------- | --------------------- | ---------- |
| 활성      | true      | NULL                  | NULL                  | NULL       |
| 탈퇴 대기 | false     | 신청 시각             | 신청 + 30일           | NULL       |
| 삭제 완료 | false     | 유지                  | 유지                  | 삭제 시각  |

CHECK 제약으로 두 예정 시각은 함께 기록되며 탈퇴 신청·삭제된 회원은 활성일 수 없습니다.
0005 이전에 비활성화된 기존 계정은 시각이 NULL이므로 복구·자동 삭제 대상이 아닙니다.

## 탈퇴 신청 — `DELETE /api/v1/auth/me`

비밀번호를 재확인한 뒤 회원 행 잠금 아래 한 트랜잭션으로 처리합니다.

- 탈퇴 대기로 전환하고 `marketing=false`, 신청·예정 시각을 기록합니다.
- 모든 로그인 계열의 Refresh와 미만료 Access를 폐기합니다. 토큰 검증은 활성 회원만
  허용하므로 대기 회원의 기존 토큰·업무 API 요청은 401입니다.
- 레시피·쿠폰·주문은 삭제하지 않습니다. 이전 CRA-34의 즉시 정리 단계는 예약 삭제로 옮겼습니다.

## 계정 복구 — 기존 `POST /api/v1/auth/login` 재사용

별도 복구 API를 만들지 않았습니다. 정책이 "비밀번호로 정상 인증하면 복구"이고, 로그인 응답이
같은 TokenPair이므로 BFF·웹 변경 없이 기존 로그인 화면으로 복구할 수 있기 때문입니다.

1. 로그인 실패 제한을 먼저 확인합니다.
2. Argon2id로 비밀번호를 검증하고, 대기 회원이면 유예 기간 안인지 DB 시각으로 확인합니다.
3. 회원 행을 `FOR UPDATE`로 잠그고 비밀번호 해시, 탈퇴 신청 시각, 유예 기간, 미삭제 상태를
   다시 확인합니다. 신청 시각이 달라졌으면 복구하지 않습니다. 따라서 탈퇴 신청 전에 비밀번호를
   검증한 로그인은 계정을 되살리지 못합니다.
4. 같은 트랜잭션에서 활성 상태로 되돌리고 탈퇴 시각을 지운 뒤 새 Access/Refresh를 저장합니다.

보존한 레시피·쿠폰·주문은 그대로 유지됩니다. 탈퇴 때 폐기한 토큰은 복구하지 않으며
`marketing`은 false로 남습니다. 유예 기간이 지났거나 삭제된 계정은 없는 계정과 같은 401입니다.
응답 형식은 일반 로그인과 같아 복구 여부를 따로 알려주지 않습니다.

## 로그인 실패 제한

| 항목      | 내용                                                                           |
| --------- | ------------------------------------------------------------------------------ |
| 기준      | 정규화한 이메일(앞뒤 공백 제거·소문자)의 SHA-256. 이메일 원문은 저장하지 않음  |
| 저장      | `login_failures` 테이블, 서버 DB. 여러 API 프로세스가 같은 기록을 공유         |
| 제한      | 연속 3회째 시도부터 10분. 제한 중에는 비밀번호를 검증하지 않음                 |
| 응답      | 429 `LOGIN_LOCKED`, `Retry-After`(남은 초), 고정 안내 문구                     |
| 초기화    | 로그인 성공 시 기록 삭제. 제한이 끝난 뒤 다시 실패하면 곧바로 10분 재제한      |
| 정리      | 하루 동안 시도가 없고 잠기지 않은 기록은 예약 작업이 삭제                      |
| 계정 노출 | 없는 이메일도 같은 기록·제한을 적용해 401·429로 계정 존재를 구분할 수 없음     |
| 동시 요청 | 비밀번호 검증 전에 행 잠금 아래 시도 수를 먼저 올려 같은 이메일 병렬 시도 차단 |

관리자 로그인(`/admin/auth/login`)과 회원 로그인은 별도 경로이며 이번 제한은 회원에만 적용합니다.
BFF는 429 상태와 코드·메시지를 전달하지만 `Retry-After` 헤더는 전달하지 않습니다.

**IP 기반 방어 검토:** 이메일별 제한은 한 계정을 노리는 대입 공격을 막지만, 여러 이메일에 흔한
비밀번호를 하나씩 시도하는 공격과 남의 계정을 일부러 잠그는 공격은 막지 못합니다. IP 기반 제한은
BFF·프록시 뒤에서 실제 클라이언트 IP를 신뢰할 수 있게 전달하는 구조가 먼저 필요합니다. 현재
FastAPI는 BFF의 IP만 보게 되므로 이번에 구현하지 않았으며 배포 구조와 함께 결정해야 합니다.

## 30일 후 예약 삭제

```sh
# 건수만 확인 (기본값). 실행 기록은 남깁니다.
uv run --directory apps/api python -m aura_api.infra.purge_members
# 실제 삭제. 한 번에 최대 500명, --limit으로 조정
uv run --directory apps/api python -m aura_api.infra.purge_members --execute
```

`AURA_DATABASE_URL`이 필요합니다. 결과가 `succeeded`가 아니면 종료 코드 1을 반환합니다.

### 회원별 처리 (회원 한 명 = 트랜잭션 하나)

1. 회원 행을 `FOR UPDATE`로 잠그고 비활성·미삭제·예정 시각 경과를 다시 확인합니다. 복구 로그인이
   먼저 커밋했으면 건너뜁니다.
2. 남은 토큰을 폐기 기록한 뒤 로그인 계열과 Refresh 행을 삭제합니다.
3. 주문과 무관한 미사용 쿠폰을 삭제합니다(`AVAILABLE`, `used_order_id IS NULL`, 주문 미참조).
4. 본인 레시피를 삭제합니다. 향료 구성은 CASCADE, 다른 회원의 파생 레시피는 부모만 해제됩니다.
5. 해당 이메일의 로그인 실패 기록을 삭제합니다.
6. 회원 행은 주문의 FK 때문에 남기고 이메일을 `deleted-<id>@deleted.invalid`, 이름을 `탈퇴회원`,
   비밀번호 해시를 로그인할 수 없는 값으로 바꾼 뒤 `deleted_at`을 기록합니다.

중간에 실패하면 그 회원의 변경은 모두 롤백되고, 다음 실행에서 다시 처리합니다. 처리 대상은
예정 시각이 지난 비활성·미삭제 회원뿐이므로 재실행해도 이미 처리한 회원과 복구한 회원은
다시 바뀌지 않습니다. 실행마다 `member_deletion_runs`에 건수·상태·실패 회원 ID를 기록합니다.

### 보존하는 데이터

- `orders`, `order_items`, `order_item_selections`와 주문이 참조하는 쿠폰: 수령인·주소·주문 스냅샷
  포함. 전자상거래 거래 기록 보존 기준을 고려해 삭제하지 않습니다.
- `admins`, `admin_sessions`: 같은 UUID여도 수정하지 않습니다.
- `atelier_drafts`(방문자 guest_id 기준), `partner_inquiries`(입점 문의): 회원 FK가 없어 범위 밖입니다.
- `revoked_tokens`: jti와 만료 시각뿐이며 만료 후 기존 정리 대상입니다.

따라서 예약 삭제 후에도 **개인정보 완전 파기 완료가 아닙니다.** 주문 개인정보의 보존 기간·분리
보관·기간 경과 후 파기는 별도 정책과 작업이 필요합니다.

## 동시성 보장

| 경합                         | 결과                                                         |
| ---------------------------- | ------------------------------------------------------------ |
| 복구 로그인이 먼저 커밋      | 삭제 작업은 잠금 대기 후 재확인에서 건너뜀. 데이터 전부 유지 |
| 삭제 작업이 먼저 커밋        | 복구 로그인은 잠금 대기 후 재확인에서 401. 데이터 전부 삭제  |
| 탈퇴 전 비밀번호 검증 로그인 | 신청 시각 불일치로 저장 거절(401). 탈퇴 상태 유지            |
| 같은 이메일 병렬 로그인      | `login_failures` 행 잠금으로 직렬화. 3회를 넘는 시도는 429   |

실제 PostgreSQL에서 두 경합 순서를 모두 재현해 일부만 복구·삭제되는 상태가 없음을 검증했습니다.

| 조정민 | 로그인 429 안내와 남은 시간 표시, 복구 안내 문구 등 BFF·웹 UX 검토                      |

결정합니다. 백업·로그에 남은 개인정보 처리도 별도 운영 정책이 필요합니다.
