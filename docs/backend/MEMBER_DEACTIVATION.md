# CRA-34 회원 계정 비활성화 및 개인 데이터 정리

이 기능은 일반 회원의 계정 사용을 중지하고 합의된 개인 데이터를 정리합니다.
개인정보 완전 파기, 이메일 재가입 허용, 계정 복구 정책을 구현한 기능은 아닙니다.

## API 계약

`DELETE /api/v1/auth/me`

검증된 회원 `Authorization: Bearer <Access JWT>`와 다음 JSON 본문이 필요합니다.

```json
{ "currentPassword": "현재 비밀번호" }
```

현재 비밀번호는 기존 로그인과 같은 1~256자이며 UTF-8 인코딩 불가능한 문자는 거절합니다.
공백 제거나 Unicode 정규화는 하지 않습니다. SecretStr로 입력 표현을 보호하고 기존
Argon2id(아르곤투아이디) 검증을 사용합니다. 회원 ID는 JWT의 sub에서만 가져옵니다.
관리자 principal 또는 admin permission이 있는 JWT는 회원 UUID와 같아도 거절합니다.

| 상황                                                | HTTP | 내용                             |
| --------------------------------------------------- | ---- | -------------------------------- |
| 성공                                                | 204  | 본문·새 토큰·Set-Cookie 없음     |
| 현재 비밀번호 불일치 또는 검증 후 해시 변경         | 400  | CURRENT_PASSWORD_INVALID         |
| 인증 실패·관리자·비활성/없는 회원                   | 401  | 기존 공통 오류, Bearer 인증 헤더 |
| CSRF 차단                                           | 403  | 기존 공통 오류                   |
| 빈 본문·누락·null·추가 필드·잘못된 타입/길이/인코딩 | 422  | 입력값 없는 일반 검증 오류       |
| 비활성화 저장소 장애                                | 503  | 성공으로 처리하지 않음           |

폐기 조회 장애는 기존 JWT 검증기의 기본 거부 정책에 따라 401입니다.
400을 사용해 비밀번호 불일치를 BFF의 401 자동 Refresh와 구분합니다. 성공 후 같은 JWT로
다시 요청하면 이미 폐기됐으므로 401이며, 무인증 요청을 성공 처리하지 않습니다.
응답 유실 뒤 임의 401을 이전 요청의 성공 증거로 해석하는 기능도 없습니다.

## 파일별 역할

- `apps/api/aura_api/api/auth.py`: DELETE 경로, SecretStr 입력 및 회원 principal 검사.
- `apps/api/aura_api/identity/service.py`: 비밀번호 재확인과 직접 호출 입력 검증.
- `apps/api/aura_api/identity/repository.py`: 비활성화 인터페이스와 미연결 저장소의 기본 거부.
- `apps/api/aura_api/identity/postgres.py`: 원자적 계정 변경·전체 폐기·쿠폰·레시피 정리.
  CRA-33과 `_revoke_user_families()`를 공유하며 기존 `_revoke_family()`를 재사용합니다.
- `apps/api/aura_api/infra/repositories/users.py`: 활성 회원 조회 및 업무 트랜잭션의 FOR SHARE 잠금.
- `apps/api/aura_api/services/orders.py`, `services/recipes.py`: 업무 트랜잭션 안에서 활성
  회원을 재확인하고 커밋까지 잠금을 유지합니다. 레시피 삭제도 같은 방식으로 보호합니다.
- `apps/api/tests/test_deactivation.py`: 기존 lifecycle 클라이언트를 재사용합니다. DB 검사는
  실제 schema.sql과 seed.sql을 테스트 전용 임시 스키마에 적용해 수행합니다.
- `apps/api/tests/test_principal_boundaries.py`: 같은 UUID의 관리자와 회원을 분리 검증합니다.
- `apps/api/tests/fixtures/storefront_app.py`: 기존 저장소 대역에 새 활성 회원 잠금 접점을 연결합니다.
  테스트 대역은 실제 PostgreSQL 잠금을 검증하지 않습니다.

## 한 번에 처리하는 DB 트랜잭션

트랜잭션은 여러 변경을 모두 성공시키거나 모두 취소하는 단위입니다.

1. 서비스에서 현재 비밀번호를 검증합니다.
2. 저장소에서 회원 행을 FOR UPDATE로 잠그고 활성 상태와 검증 당시 해시를 다시 확인합니다.
3. is_active=false, marketing=false로 변경합니다.
4. 본인 로그인 계열을 ID 순서로 잠그고 계열·Refresh를 폐기합니다.
5. 각 계열에서 발급된 모든 미만료 Access jti를 revoked_tokens에 기록합니다.
6. 본인 소유이며 AVAILABLE, used_order_id IS NULL, 주문에서도 참조하지 않는 쿠폰만 삭제합니다.
7. 본인 recipes를 삭제합니다. recipe_ingredients는 CASCADE로 삭제됩니다. 다른 회원의
   파생 레시피는 행을 보존하고 parent_id만 SET NULL로 해제합니다.
8. 커밋(확정 저장)이 끝난 뒤에만 성공합니다. 실패하면 앞선 변경과 FK에 따른 변경도 롤백합니다.

users 행·기존 이메일 UNIQUE·주문·주문 항목·주문 구성 스냅샷은 유지합니다. 사용 쿠폰과 주문
참조 쿠폰도 유지합니다. admins와 admin_sessions는 수정하지 않습니다. 기존 스키마·ORM·
마이그레이션·인프라·BFF 운영 코드는 변경하지 않습니다.

## 동시 요청과 잠금

기본 잠금 순서는 회원 → 계열 → 토큰입니다. 로그인 저장은 검증 당시 해시와 활성 상태를
회원 FOR SHARE 잠금 아래 재확인합니다. Refresh도 회원 잠금을 먼저 잡습니다.

- 탈퇴가 먼저 잠금을 잡으면 대기하던 로그인·Refresh·비밀번호 변경·프로필 수정은 변경 후
  활성 상태/해시를 재확인해 거절합니다.
- 로그인이나 Refresh가 먼저 커밋하면 비활성화가 그 새 계열 또는 토큰까지 폐기합니다.
- 비밀번호 변경이 먼저 끝나면 이전 비밀번호 검증에 근거한 비활성화는 400으로 거절합니다.
- 주문·쿠폰 사용·레시피 저장은 별도 업무 트랜잭션 안에서 회원 FOR SHARE 잠금을 먼저 잡고
  활성 상태를 확인합니다. 탈퇴가 먼저면 쓰기는 401입니다. 업무가 먼저면 탈퇴가 기다렸다가
  주문은 보존하고 쿠폰 사용 이력은 유지하며 저장된 개인 레시피는 정리합니다.
- 프로필 UPDATE는 회원 행 잠금과 is_active 조건으로 직렬화됩니다.

업무 요청의 초기 JWT 인증만으로는 탈퇴와의 경쟁을 막을 수 없습니다. 업무 트랜잭션 안의
재확인과 잠금이 필요합니다. 다른 회원 레시피의 부모 연결에 따른 FK 잠금 등으로 DB가
교착·타임아웃을 감지하면 성공 처리하지 않고 롤백합니다. 인증이 이미 끝난 모든 읽기 요청을
강제 취소하는 기능은 아닙니다.

## 남겨둔 데이터와 미확정 정책

이름·이메일·비밀번호 해시, 주문의 수령인·주소·사용자 입력 스냅샷은 이번에 삭제하지 않습니다.
UUID로 연결된 기록이 남으므로 익명화 또는 개인정보 완전 삭제 완료라고 표시하지 않습니다.

다음은 별도 합의 대상입니다.

- 주문 개인정보의 보존 목적·최소 범위·기간·관리자 노출·정리 절차
- 이메일 재가입 허용과 혜택 재지급, 계정 복구·재연결
- 정지와 탈퇴의 상태 구분 및 탈퇴 시각 기록
- 개인정보 완전 파기와 백업·로그 데이터 처리

기존 이메일은 유지하므로 현재 회원가입 중복 검사는 해당 이메일에 409를 반환합니다.
이를 향후 재가입 정책이 확정됐다는 의미로 해석하지 않습니다. 탈퇴 계정의 새 인증은 거절돼
주문을 조회할 수 없지만 관리자 주문 화면에는 기존 데이터가 남습니다.
방문자 guest_id로 저장되는 초안은 회원 FK가 없으므로 임의로 삭제하지 않습니다.

## BFF·화면 후속 작업

정민님 연결 범위는 BFF DELETE 경로, 비밀번호 확인 화면, 회원 쿠키 삭제, 계정·주문·레시피
캐시 정리, 장바구니 등 브라우저 데이터 초기화입니다. 백엔드 204 확인 후에만 완료 안내를
표시하고, 기존 회원 인증 Web Lock으로 Refresh·로그아웃과 직렬화해야 합니다.
관리자 쿠키는 지우지 않습니다. 다른 기기는 토큰 검증에서 차단되며 그 기기의 화면·쿠키를
서버가 직접 지우는 것은 아닙니다. 개인정보 삭제 완료라는 안내는 사용하지 않습니다.
Linear CRA-34는 최종 개인정보 정책 확정 전 Done 처리하지 않습니다.

## 검증

전체 API 검사는 DB 접속을 비활성화해 실행합니다. 실제 DB 검사는 실행 중인
aura-jwt-test-db가 127.0.0.1:5434로만 연결됨을 확인한 뒤 전용 접속 정보와
AURA_ALLOW_DATABASE_TESTS=1을 설정해 수행합니다. 테스트마다 auth_test_ 접두사의 임의
스키마를 만들고 그 스키마만 정리합니다. public 초기화나 마이그레이션 롤백은 실행하지 않습니다.
운영·공유 DB에는 접속하지 않습니다.

2026-10-27 검증 결과입니다. 실행 사이의 중복 테스트 수는 합산하지 않습니다.

| 탈퇴·비밀번호 변경·프로필·lifecycle 집중 회귀, 메모리 및 격리 PostgreSQL |  224 |    0 |   24 |

Ruff와 Python 116개 파일 포맷 검사가 통과했습니다. 실제 PostgreSQL에서는 운영 스키마
정의를 그대로 임시 스키마에 적용해 다음을 검증했습니다.

- 비활성화·마케팅 해제·모든 계열/Refresh 폐기와 미만료 Access jti의 실제 폐기 기록
- 사용 쿠폰과 주문 스냅샷 보존, 쿠폰 삭제의 네 조건, 다른 회원 쿠폰 유지
- 본인 레시피/향료 삭제, 다른 회원 레시피·향료 보존과 부모 SET NULL
- 마지막 레시피 삭제에 실패하는 DB 트리거를 주입한 뒤 계정·쿠폰·토큰까지 전체 롤백
- 같은 UUID의 관리자 세션 유지 및 관리자 JWT로 회원 비활성화 차단
- 비활성화와 로그인·Refresh·비밀번호·프로필·주문·레시피의 경쟁 및 실제 잠금 대기

최종 탈퇴 모듈 64개 사례 중 PostgreSQL 매개변수 32개는 모두 통과했습니다. 메모리
매개변수는 18개 통과, 실제 FK·잠금·롤백 등이 필요한 14개를 건너뛰었습니다.
전체 API 실행의 173개 건너뜀에는 기존 DB 테스트와 PostgreSQL 매개변수가 포함됩니다.
기존 Windows asyncio 정책 폐기 예정 경고 2개가 있습니다.

웹 lint·CSS·타입 검사와 `npm run build`가 통과했습니다. 기존 JWT·업무 E2E는 실제
FastAPI/BFF와 저장소 대역을 사용하므로 실제 DB E2E나 새 DELETE의 브라우저 검증으로
표시하지 않습니다. 새 BFF DELETE 경로·화면은 후속 작업입니다.

루트 `npm run check`는 기존 283개 파일의 Prettier 경고로 포맷 단계에서 중단됐습니다.
변경 문서 2개는 별도 포맷 검사를 통과했습니다. 무관한 파일을 일괄 수정하지 않았습니다.
빌드는 로컬 Next.js 16.4.2에서 통과했으며 선언/잠금의 16.4.3과 일치하는 CI 환경에서
추가 확인이 필요합니다. `git diff --check`도 통과했습니다.
